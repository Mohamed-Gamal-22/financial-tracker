> ملحوظة: كل الـ requests ممكن تاخد `?lang=ar` في الـ query عشان رسائل الأخطاء ترجع بالعربي. استخدميها ثابتة في كل استدعاء.

## شكل الـ Response العام

**نجاح (مع بيانات):**
```json
{ "message": "Done", "success": true, "status": 200, "data": {} }
```
**نجاح (من غير بيانات):**
```json
{ "message": "Password reset successfully", "success": true, "status": 200 }
```
**فشل:**
```json
{ "message": "Validation Error", "success": false, "status": 400, "errors": {} }
```
`stack` (تفاصيل الخطأ التقنية) بترجع بس في Development، مش في Production — متعتمديش عليها في عرض رسائل للمستخدم.

**مثال خطأ تحقق (Validation):**
```json
{
  "message": "Validation failed",
  "success": false,
  "status": 400,
  "errors": [
    { "key": "body", "issues": [
      { "path": "email", "message": "Invalid email address" }
    ]}
  ]
}
```

# 1. Authentication (`/auth`)

## 1.1 إنشاء حساب — `POST /auth/signup`

**Body:**
```json
{
  "fullname": "Omar Ali Ali",
  "email": "user@example.com",
  "password": "Raneem123@",
  "confirmPassword": "Raneem123@",
  "role": 0
}
```
| الحقل | إلزامي | القاعدة |
| --- | --- | --- |
| fullname | ✅ | كلمتين بالظبط، مفصولين بمسافة واحدة، حروف إنجليزي فقط |
| email | ✅ | إيميل صحيح — هو المعرّف الفريد للحساب |
| password | ✅ | 8 خانات على الأقل، حرف كبير + صغير + رقم + رمز خاص |
| confirmPassword | ✅ | يطابق الباسورد بالظبط |
| role | ❌ | `0 = USER` (افتراضي)، `1 = ADMIN` — الفرونت العادي **ميبعتش الحقل ده أبدًا** |

الحساب **مش بيتسجل في الداتا بيز فورًا** — بيتخزن مؤقت في Redis 24 ساعة لحد تأكيد الإيميل بالـ OTP.

---

## 1.2 تسجيل الدخول بجوجل (Signup أو Login) — `POST /auth/gmail`

**استخدمي ده في زرار "الدخول بجوجل" الوحيد في الواجهة** — بيغطي الحالتين تلقائيًا:
- حساب جوجل جديد → بينشئ ويسجل دخول فورًا.
- حساب جوجل موجود → بيسجل دخول.
- حساب موجود بإيميل/باسورد عادي → **مرفوض** (الحساب اتعمل بطريقة تانية).

**Body:**
```json
{ "idToken": "..." }
```
`idToken` هو Google ID Token من Google Sign-In SDK في الفرونت.

**Google Client ID (من توثيق الباك إند):**
```
189623563111-jc2s82i3j7n6mfgpd5vcfeig9r65afjr.apps.googleusercontent.com
```
استخدمي نفس الـ Client ID ده بالظبط في إعداد Google Sign-In بالفرونت.

---

## 1.3 تسجيل الدخول — `POST /auth/login`

**Body:**
```json
{ "email": "user@example.com", "password": "Raneem123@" }
```
بيرجع `access_token` و `refresh_token` جوه `data` — بس لو الإيميل متأكد.

---

## 1.4 تسجيل الدخول بجوجل (لمستخدم موجود بس) — `POST /auth/login/gmail`

**Body:** نفس شكل 1.2. الفرق: ده بيرفض لو الحساب مش موجود مسبقًا (مبيعملش حساب جديد). **الاستخدام المقترح: متستخدميهوش في الواجهة العادية، استخدمي 1.2 بس.**

---

## 1.5 تأكيد الإيميل — `PATCH /auth/confirm-email`

**Body:**
```json
{ "email": "user@example.com", "otp": "722104" }
```
لو الكود صح، الحساب بيتسجل فعليًا في الداتا بيز ويتعلّم كـ verified، وبيتمسح كل داتا Redis المؤقتة.

---

## 1.6 إعادة إرسال كود التأكيد — `PATCH /auth/resend-otp`

**Body:**
```json
{ "email": "user@example.com" }
```

**قواعد الـ OTP (سارية هنا وفي نسيان الباسورد كمان):**
- صالح **5 دقايق** — مينفعش تطلبي كود جديد قبل ما القديم ينتهي.
- أقصى **5 طلبات**، بعدها **حظر 10 دقايق** وعداد الطلبات بيتصفّر.

---

## 1.7 نسيت كلمة المرور (إرسال OTP) — `POST /auth/forgot-password-otp`

**Body:**
```json
{ "email": "user@example.com" }
```
متاح بس لمستخدمين سجلوا بإيميل/باسورد (مش جوجل) ومؤكدين إيميلهم. نفس قواعد الـ OTP فوق.

---

## 1.8 تغيير كلمة المرور — `PATCH /auth/reset-password`

**Body:**
```json
{
  "email": "user@example.com",
  "otp": "145229",
  "password": "NewPass123@",
  "confirmPassword": "NewPass123@"
}
```
بعد النجاح: الباسورد بيتغير، **كل الجلسات بتتقفل**، والفرونت لازم يوجّه المستخدم لشاشة Login تاني.

# 2. User (`/user`)

## 2.1 بيانات البروفايل — `GET /user`
**Header:** `Authorization: Bearer <access_token>`

## 2.2 تسجيل الخروج — `POST /user/logout`
**Header:** `Authorization: Bearer <access_token>`
**Body:** `{ "flag": "one" }` أو `{ "flag": "all" }` (جهاز واحد / كل الأجهزة). اعملي زرارين منفصلين في شاشة الحساب.

## 2.3 تجديد التوكن — `POST /user/rotate-token`
**Header:** `Authorization: Bearer <refresh_token>` **(مش access token)**
**⚠️ شرط:** بيشتغل بس لو الـ access token باقيله 5 دقايق أو أقل على الانتهاء. اعملي timer/interceptor يجدد تلقائي قبل الانتهاء، مش تستني 401.
بيرجع access_token و refresh_token جداد — خزّنيهم بدل القدامى فورًا.

## 2.4 تجميد الحساب — `DELETE /user/freeze`
**Header:** `Authorization: Bearer <access_token>`
Soft delete (بيتحط `deletedAt`). زرار أحمر + confirmation dialog إجباري.

## 2.5 رفع/تعديل صورة البروفايل — `PATCH /user/profile-pic`
**Header:** `Authorization: Bearer <access_token>` + `Content-Type: multipart/form-data`

**Form Data:**
| Key | النوع | إلزامي |
| --- | --- | --- |
| **file** | File | ✅ |

**⚠️ مهم جدًا:** اسم الحقل في الـ form-data هو **`file`**، مش `profilePic` — ده الاسم الفعلي المستخدم في الكولكشن، خدي بالك الأجنت يستخدم `file` بالظبط.

الحد الأقصى لحجم الملف: **5MB**. لو المستخدم عنده صورة قديمة، بتتمسح تلقائيًا من التخزين قبل رفع الجديدة — نفس الـ endpoint لأول رفع واستبدال.

**Response:** `{ "success": true, "data": { "url": "https://res.cloudinary.com/..." } }`
> لاحظي: الـ response هنا من غير `message` و `status` زي باقي الـ endpoints.

## 2.6 حذف صورة البروفايل — `DELETE /user/profile-pic`
**Header:** `Authorization: Bearer <access_token>`
**فشل (لو مفيش صورة أصلاً):** `{ "success": false, "message": "You don't have a profile picture" }` — Status 404. اخفي/عطّلي الزرار لو الـ profile مفيهوش صورة أصلاً.

## 2.7 تعديل الاسم — `PATCH /user/name`
**Header:** `authorization: <access_token>`
**Body:** `{ "fullname": "الاسم الجديد" }`

# 3. Category (`/category`) — ⚠️ مش موجودة في آخر كولكشن خالص

**تنبيه مهم:** آخر كولكشن اتبعتلي **مفيهوش فولدر Category خالص** — مش قراءة فقط، مش أي حاجة، الفولدر كله مش موجود. ده تغيير غريب لأن **الـ Transaction والـ Monthly Budget الاتنين بيعتمدوا على `category` ID** كحقل إلزامي (`category` في إضافة معاملة، والتصنيفات في التقارير/الملخص). من غير endpoint تجيبي بيه قايمة التصنيفات، مش هينفع تبني شاشة اختيار تصنيف أصلاً.

**الأرجح إن ده خطأ تصدير (Export) من Postman مش تغيير حقيقي في الباك إند** — التصنيفات مرّت قبل كده بمراحل كتير (ثابتة → قابلة للتعديل → قراءة فقط)، فمحتمل جدًا يكون فولدر الـ Category موجود لسه على السيرفر بس مانسيتش ضمن الفولدر اللي اتصدّر هنا.

**لازم قبل أي حاجة تانية:** تأكدي من الباك إند إن `GET /category` (و `GET /category/:id`) لسه شغالين، وابعتيلي كولكشن جديد لو اتأكد إنهم موجودين عشان أضيفهم هنا. لحد ما يتأكد ده، استخدمي التوثيق ده كمرجع مؤقت (كان آخر نسخة مؤكدة قراءة فقط):
- `GET /category` — يرجع كل تصنيفات المستخدم.
- `GET /category/:id` — تصنيف واحد بالتفصيل.
كل تصنيف بيرجع: `_id`, `name`, `type` (`income`/`expense`/`savings`).

# 4. Transaction (`/transaction`) — فيه قواعد عمل معقدة، أهم جزء في الملف ده

**⚠️ القسم ده لازم الأجنت يقراه بتركيز شديد** — المعاملات مربوطة بمنطق ميزانية معقد، ومش مجرد CRUD بسيط.

## 4.1 إضافة معاملة — `POST /transaction`
**Body:**
```json
{ "title": "استلام الراتب", "amount": 15000, "category": "6a84a5c9af7b471e4e64d5c0", "date": "2026-12-01" }
```
| الحقل | إلزامي | القاعدة |
| --- | --- | --- |
| title | ✅ | حرف واحد على الأقل |
| amount | ✅ | أكبر من 0 |
| category | ✅ | ID تصنيف موجود |
| date | ❌ | لو مبعتّهاش، الوقت الحالي |

### قواعد العمل (Business Rules) — إجبارية على الباك إند، الفرونت لازم يعرضها كأخطاء واضحة:

**١) أول معاملة في الشهر لازم تكون دخل (Income):**
لو مفيش أي معاملات في الشهر ده، أي محاولة إضافة `expense` أو `savings` **هترفض**. لازم أول معاملة تكون `income`.

**٢) لو المعاملة دخل (income):**
- لو فيه ميزانية شهرية موجودة: **إجمالي الدخل الجديد لازم يفضل ≥ سقف المصروف بالميزانية**.
- مثال: سقف المصروف 10,000، الدخل الحالي 8,000، دخل جديد 1,000 → الإجمالي 9,000 < 10,000 → **مرفوض**.

**٣) لو المعاملة مصروف (expense):**
- لو فيه ميزانية: **إجمالي المصروفات لازم ميتعديش سقف المصروف**.
- لو مفيش ميزانية: **(المصروفات + الادخار) لازم ميتعدوش الدخل**.

**٤) لو المعاملة ادخار (savings):**
- لو فيه ميزانية: **المتاح للادخار = الدخل − سقف المصروف**، والادخار الجديد لازم ميتعداش المتاح ده.
- لو مفيش ميزانية: **(المصروفات + الادخار) لازم ميتعدوش الدخل**.

**كل رفض بيرجع خطأ من الباك إند برسالة واضحة — الفرونت لازم يعرض رسالة الخطأ دي للمستخدم مباشرة (زي "الدخل المتاح غير كافٍ لتغطية هذه المعاملة")، مش رسالة عامة.**

---

## 4.2 تعديل معاملة — `PATCH /transaction/:id`
**Body:** أي حقل اختياري من `title`, `amount`, `category`, `date`.

**قواعد العمل عند التعديل:** الباك إند بيقارن المعاملة **القديمة** بـ**الجديدة** (نوع التصنيف، المبلغ، التاريخ) ويعيد فحص نفس قواعد قسم 4.1 (دخل/مصروف/ادخار) على القيم الجديدة.

**تغيير نوع التصنيف مسموح** (زي `income → expense`)، وبيتفحص حسب النوع الجديد.

**تغيير التاريخ:** بيغيّر الشهر اللي المعاملة تابعة له (مثلاً من أغسطس لسبتمبر) — الباك إند بيعيد حساب الميزانيات لكل شهر اتأثر (القديم والجديد).

**خلاصة للفرونت:** فورم التعديل لازم يبعت بس الحقول اللي اتغيّرت فعلاً، ويكون جاهز يعرض رسالة خطأ واضحة لو التعديل كسر قاعدة من قواعد الميزانية.

---

## 4.3 حذف معاملة — `DELETE /transaction/:id`
بعد الحذف، الباك إند بيعيد حساب أرقام الشهر:
- حذف **دخل**: ممكن يترفض لو باقي الدخل بقى مش كافي لتغطية سقف المصروف الحالي أو (مصروف+ادخار).
- حذف **مصروف/ادخار**: عادة بيقلل الإجمالي، ونادرًا ما يترفض.

**يعني:** حتى زرار "حذف" لازم يتعامل مع احتمال رجوع خطأ من الباك إند، مش يفترض النجاح دايمًا.

---

## 4.4 عرض معاملة واحدة — `GET /transaction/:id`
بيرجع الـ `category` **كاملة (populated)** مع `typeLabel`، مش الـ ID بس.

---

## 4.5 عرض كل المعاملات (مع فلاتر) — `GET /transaction`
مرتبة **الأحدث أولًا** دايمًا.

| Parameter | إلزامي | افتراضي | القاعدة |
| --- | --- | --- | --- |
| page | ❌ | 1 | رقم صحيح ≥ 1 |
| limit | ❌ | 10 | رقم صحيح، 1 لحد 100 |
| categoryType | ❌ | — | `income`/`expense`/`savings` (إنجليزي بس، ماتبعتيش عربي) |
| categoryName | ❌ | — | بحث جزئي غير حساس لحالة الأحرف، بيدعم عربي كمان |
| month | ❌ | — | `YYYY-MM` |

كل الفلاتر تتجمع مع بعض: `GET /transaction?page=1&limit=10&categoryType=expense&categoryName=Food&month=2026-07`

---

## 4.6 ملخص المعاملات — `GET /transaction/summary`
**Query:** `month` (اختياري، `YYYY-MM`) — لو معدّتش، بيرجّع الشهر الحالي تلقائيًا (الفرونت مش محتاج يحسبه).

بيرجع مجمّع حسب التصنيف في 3 أقسام: `expense`, `income`, `savings` — لكل تصنيف: بياناته، عدد المعاملات، والإجمالي.

---

## 4.7 تقرير يومي/شهري — `GET /transaction/report`

| Parameter | إلزامي | الوصف |
| --- | --- | --- |
| type | ❌ | `day` أو `month` |
| date | لو `type=day` | `YYYY-MM-DD` |
| month | لو `type=month` | `YYYY-MM` |

**3 حالات:**
- بدون Query params → الشهر الحالي تلقائي.
- `?type=day&date=2026-08-13` → تقرير يوم كامل (لازم `date`).
- `?type=month&month=2026-07` → تقرير شهر كامل (لازم `month`).

بيرجع `expense`/`income`/`savings` مجمّعين حسب التصنيف، بالإضافة لـ `totalExpense`/`totalIncome`/`totalSavings` جاهزين.

المعاملات والتصنيفات المحذوفة **مستبعدة تلقائيًا**.

# 5. Monthly Budget (`/monthlyBudget`) — قواعد عمل معقدة برضو

## 5.1 إنشاء ميزانية شهرية — `POST /monthlyBudget`
**Body:**
```json
{ "month": "2026-08", "expenseAmount": 14500 }
```
| الحقل | إلزامي | القاعدة |
| --- | --- | --- |
| month | ✅ | `YYYY-MM` |
| expenseAmount | ✅ | ≥ 0 |

### قواعد العمل:
1. **ميزانية واحدة بس لكل شهر** — لو موجودة، خطأ `409`.
2. **الشهر لازم يكون فيه دخل مسجل** قبل عمل ميزانية له — وإلا خطأ `400`.
3. **سقف المصروف ≤ إجمالي الدخل** في الشهر ده.
4. **سقف المصروف ميقلّش عن المصروفات الموجودة فعلاً** في الشهر ده (لو فيه معاملات مصروف مسجلة قبل الميزانية).
5. **المتاح للادخار = الدخل − سقف المصروف** (بيتحسب تلقائي).
6. **الادخار الموجود فعلاً في الشهر ميعديش المتاح للادخار** (نفس رقم 5) — وإلا الإنشاء يترفض.
7. بعد الإنشاء، `savingsAmount` (الادخار المخطط) = الدخل − سقف المصروف.

---

## 5.2 تعديل ميزانية شهرية — `PATCH /monthlyBudget/:id`
**Body:** `expenseAmount` و/أو `month` (على الأقل واحد).

- **الميزانية لازم تخص المستخدم الحالي** وإلا `404`.
- **تقدري تنقلي الميزانية لشهر تاني** (تغيير `month`) — بس مينفعش الشهر الجديد يبقى ليه ميزانية أصلاً (نفس قاعدة "ميزانية واحدة لكل شهر").
- الشهر الجديد (لو اتغيّر) لازم يكون فيه دخل برضو.
- **أقصى سقف مصروف مسموح = إجمالي الدخل − الادخار الفعلي الموجود بالفعل**.
- **سقف المصروف الجديد ميقلّش عن المصروفات الفعلية الموجودة**.
- الادخار المخطط بيتحسب تلقائي تاني (دخل − سقف مصروف جديد).

---

## 5.3 حذف ميزانية شهرية — `DELETE /monthlyBudget/:id`

**قاعدة مهمة:** **مينفعش تحذفي ميزانية لو الشهر بتاعها فيه مصروفات أو ادخار مسجل فعلاً** (`actualExpenses > 0` أو `actualSavings > 0`) — خطأ `400`. يعني زرار "حذف الميزانية" لازم يكون معطّل أو يوري تحذير واضح لو الشهر ده فيه معاملات فعلية.

---

## 5.4 عرض ميزانية واحدة — `GET /monthlyBudget/:id`
بيرجع الحقول الأساسية + **4 حقول محسوبة**:
```json
{
  "_id": "...", "month": "2026-08",
  "expenseAmount": 15000, "savingsAmount": 5000,
  "actualExpenses": 8000, "actualSavings": 2000,
  "remainingExpenseBudget": 7000, "remainingSavings": 3000
}
```

## 5.5 عرض كل الميزانيات — `GET /monthlyBudget`
بيرجع `{ "budgets": [...], "total": {...} }` — مرتبة من الأحدث للأقدم، كل عنصر بنفس شكل 5.4.

## 5.6 عرض ميزانية شهر محدد — `GET /monthlyBudget/month?month=2026-08`
نفس شكل الاستجابة في 5.4 بس لشهر واحد بالتحديد.

# ملاحظات ختامية للأجنت

1. **أهم حاجة في الملف ده:** قواعد الميزانية والمعاملات (قسم 4 و5) — دي مش validation بسيط، دي منطق مالي مترابط. أي فورم لإضافة/تعديل معاملة أو ميزانية لازم يتعامل مع رفض الباك إند كحالة متوقعة وطبيعية، ويعرض رسالة الخطأ اللي راجعة من الـ API مباشرة للمستخدم بدل رسالة عامة.
2. **الكاتيجوري مش موجودة في آخر كولكشن خالص** — على الأغلب خطأ تصدير مش تغيير حقيقي، بس **لازم تتأكدي قبل ما تكملي** لأن باقي الشاشات (معاملات، ميزانية) معتمدة عليها بالكامل.
3. **الـ Google Client ID موجود فوق** في قسم 1.2 — سلّميه للي بيظبط إعداد Google Sign-In في الفرونت.
4. **استخدمي `?lang=ar`** في كل الـ requests عشان رسائل الأخطاء ترجع بالعربي جاهزة للعرض.
5. **رفع صورة البروفايل:** اسم الحقل `file` مش `profilePic` — غلطة شائعة لو مش منتبه.
